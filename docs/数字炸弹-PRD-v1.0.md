# 数字炸弹 PRD v1.3

版本日期：2026-10-26 ｜ 状态：首版开发评审稿 ｜ 平台：微信小游戏，手机竖屏

本文保留已明确的核心需求：双人各设四位谜底、交替猜测、仅相同位置的相同数字计为命中、同一大轮给予双方等量猜测机会，双方均猜中则平局；提供在线匹配、密码匹配，以及准备、猜测、结果三个阶段；首版不接广告。

未由需求明确的规则均为本文的首版建议默认值，可在开发前调整。引擎已由用户确认采用 Cocos Creator + TypeScript，本机开发版本锁定 Cocos Creator 3.8.8。玩法与服务端需求保持不变。

## 1. 产品定位与目标

一款面向朋友约战和陌生人快速对战的双人数字推理小游戏。玩家通过有限的命中数量反馈，逐步推导对方的四位密码；紧张感来自交替行动、倒计时和破解进度。

“数字炸弹”是包装主题，不是猜数字区间、不断缩小上下限的传统玩法。首屏副标题使用“设下四位密码，抢先破解对手”，避免认知误差。

首版验证三个问题：玩家是否理解反馈规则、推理过程是否有趣、结束后是否愿意再玩。单局目标时长暂定 3～8 分钟，这是待实测目标，不是已验证的玩法结论。

### 1.1 用户与场景

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| 熟人玩家 | 两位好友约好一起玩 | 输入口令即可同房，快速再来一局 |
| 休闲玩家 | 碎片时间找人对战 | 匹配方便、规则易懂、等待可退出 |
| 推理爱好者 | 通过多次尝试排除组合 | 历史清晰、反馈准确、胜负可信 |

### 1.2 首版范围

P0：身份登录、头像昵称编辑、随机延时人机兜底、第一视角牌桌及基础动效、大厅、玩法说明、在线匹配、口令房、设置谜底及准备、交替猜测、历史记录、超时、认输、断线恢复、结算、再来一局、基础设置、服务端监控与关键埋点。

P1：用户主动分享房间卡片、结算卡片、个人战绩页。首版无这些功能也可完成闭环；口令可由玩家自行告诉好友。

不做：广告、付费、货币、道具、复活、提示购买、排位、排行榜、聊天、好友系统、观战、多人局、局中 AI 接管、单机模式、赛季任务和复杂装扮。首版不预留可见广告入口。

## 2. 完整玩法规则

### 2.1 谜底与反馈

| 项目 | 首版默认规则 |
| --- | --- |
| 人数 | 固定两人 |
| 谜底 | 恰好四位数字，每位为 0～9 |
| 重复数字 | 允许，如 1122、0000 |
| 前导零 | 允许，如 0123；所有数字按字符串保存 |
| 谜底设置 | 两人各自设置，只在双方锁定后开始 |
| 修改 | 锁定前可改，锁定后本局不可改 |
| 猜测 | 每次提交恰好四位数字，轮到自己时才能提交 |
| 反馈 | 只给出“命中 N/4”，不标出正确的是哪一位 |
| 错位数字 | 即使数字存在于谜底中，位置不同也不计分 |
| 获胜 | 后手单独猜中立即获胜；先手猜中后给后手本大轮的一次补猜，补猜也中则平局，否则先手胜 |
| 重复猜测 | 允许但二次提醒，仍消耗本次行动；不重置倒计时 |

判定公式：`hit_count = Σ(guess[i] == secret[i])，i = 0..3`。

示例：谜底为 `0123` 时，猜 `0453` 命中 2/4，猜 `1230` 命中 0/4，猜 `0123` 命中 4/4。谜底 `1122`、猜测 `1212`，命中 2/4。界面不能把示例中的正确位置高亮作为实际对局反馈。

允许重复后有 10,000 种谜底组合，输入规则简单，但仅反馈数量的推理难度较高。内测必须观察玩家平均猜测次数及流失；若需要调整为不重复数字，应作为下一版整套规则变更，不能让不同玩家在同一队列使用不同规则。

### 2.2 先后手与对局长度

- 双方锁定谜底后，服务器等概率随机选择先手，显示“你先猜”或“对手先猜”。
- 行动顺序严格交替。先手在本大轮猜中后进入“后手补猜”，不立刻结算、不揭晓任何谜底；后手使用本大轮尚未使用的一次机会，拥有正常的 30 秒，不额外增加机会总数。
- 后手补猜命中 4/4 则平局；有效提交但未猜中、补猜超时、认输或离线判负均为先手胜。不继续下一大轮。
- 若先手未猜中，后手在正常行动中猜中，立即判后手胜；先手不再补猜，因为双方已获得同等行动机会。
- 补猜期间显示“对手已破解，你还有最后一次机会”；先手显示“已破解，等待对手最后一次猜测”。双方谜底必须等最终结算才揭晓。
- 补猜降低先后手带来的机会数差异，但不宣称完全消除策略优势；实际平衡通过真人局数据评估。
- 同一房间双方再来一局时交换先后手；重新匹配或新建房间时重新随机。
- 一个“大轮”包含双方各一次行动机会；界面显示“大轮 3/20”及“我的第 3 次机会”，避免轮次歧义。
- 建议最多 20 个大轮。第 20 大轮双方均未猜中则平局，不根据最高命中数强行判胜。此上限是为避免无限拖局而增加的首版建议，不属于原始必需规则。
- 每次行动 30 秒，因此猜测阶段理论上限约 20 分钟，另加少量状态切换时间。若实测普遍超出目标时长，应调整规则后重新验证，不能仅通过缩短操作时间掩盖难度。

### 2.3 倒计时与结束原因

| 项目 | 默认值及行为 |
| --- | --- |
| 设置谜底 | 两人到齐后共同开始 60 秒倒计时 |
| 准备超时 | 未全部锁定则取消本局，不计胜负；已锁定者可返回大厅 |
| 回合超时 | 记为一次空过，计入行动机会，不生成猜测数字或命中数 |
| 连续超时 | 某玩家连续两次自己的行动机会超时，判该玩家负；有效提交清零其连续超时次数 |
| 主动认输 | 游戏开始后需确认，提交成功即判负 |
| 上限平局 | 第 20 大轮双方均未猜中则平局；若先手猜中，先完成后手补猜再结算 |
| 同轮破解平局 | 先手猜中后，后手本轮补猜也中，判平局 |
| 系统故障 | 无法恢复权威状态时中止，不计胜负 |

以服务器接收并串行处理的时间为准：仅接受在截止时刻之前到达的有效提交；到达截止时刻及之后视为超时。客户端提交动画不代表成功，网络慢不会自动延长时间。重试不重复消耗行动。

## 3. 页面与流程

主流程：启动 → 登录/恢复对局 → 大厅 → 在线匹配或口令房 → 双人准备 → 猜测 → 结果 → 再来一局或大厅。

页面组成：启动加载页、个人资料页、大厅、匹配浮层、好友房、准备页、对战页、结果页；说明、设置、认输、网络恢复采用弹层。

### 3.1 启动与身份

- 使用微信登录凭据由服务端建立用户身份与游戏会话，凭据失败可重试，不能在未登录状态进入匹配。
- 首次进入优先展示“使用微信头像昵称”入口，由用户点击触发平台允许的资料获取/授权流程；已获有效授权且能力允许时复用资料，不反复弹窗。账号登录与个人资料获取分离。
- 获取有效头像昵称后用于初始资料；拒绝、取消、不支持、失败或超时后使用系统头像和“玩家 3816”等昵称，允许直接继续。头像或昵称只有一项有效时，另一项单独兜底。
- 已有用户自定义资料优先级最高，重新登录不得被微信资料覆盖；用户可在个人页主动重新同步。默认请求仅首次引导，不在每次匹配前请求。
- 技术预研必须验证“微信小游戏”的资料 API、授权条件和目标基础库，不能直接套用小程序的 WXML 头像填写方案。此次检索未能直接读取微信官方页面，不把任何特定接口取得真实资料的能力写成已验证结论；能力不可用时按默认资料及手动编辑流程上线。待核验入口：[用户资料](https://developers.weixin.qq.com/minigame/dev/api/open-api/user-info/wx.getUserInfo.html)、[资料按钮](https://developers.weixin.qq.com/minigame/dev/api/open-api/user-info/wx.createUserInfoButton.html)。
- 新用户首次展示一页规则：设置四位数 → 交替猜 → 只看数字与位置同时命中的数量。提供上述示例，可从大厅重复查看。
- 登录后先查询进行中对局；存在则恢复，防止重复排队或占用多个房间。
- 提供隐私说明、用户协议与反馈入口；具体账号主体、平台要求及所需能力在提审前核实。

### 3.1.1 个人资料编辑

- 点击大厅头像进入个人页，可修改头像和昵称；免费，不影响账号身份或战绩。
- 头像支持系统预设、重新获取微信头像，以及通过小游戏可用图片选择能力上传自定义图片；具体平台能力在 M0 验证。上传提供方形裁剪预览，服务端校验类型和大小，建议压缩为 256×256，上传上限 2MB。
- 昵称默认限制 2～12 个可见字符，支持中文、英文、数字，按可见字符计数；禁止空白昵称、控制字符及违规内容，允许重名。前后端规则一致。
- 上传头像与昵称需经过内容校验/审核后对其他玩家生效；处理中保留旧资料，失败可重试，不影响匹配。微信导入资料也走统一保存和展示流程。
- 保存按钮有提交/成功/失败状态；修改成功跨设备同步，取消编辑不覆盖旧资料。进行中的对局使用开局资料快照，修改从下一局生效。
- 用户资料默认仅用于该用户身份展示；用于自动对手展示需额外明确授权、可撤回，不能因用户注册即默认复用。分析埋点不记录原始头像和昵称。

### 3.2 大厅

页面核心按钮：“在线匹配”“好友对战”。辅助入口：“个人资料”“怎么玩”“声音与振动”“隐私与反馈”。设置放在左下辅助区；右上角仅背景，不放自定义按钮或重要信息，为微信原生胶囊让位。不显示虚构在线人数。

在线匹配按钮进入匹配浮层；好友对战提供“创建口令房”“输入口令加入”。登录中、维护中和已有对局时，相关按钮须显示明确状态，避免可点无响应。

### 3.3 在线匹配

- 首版单一区域、单一规则队列，优先按等待时间配对，不做段位分层。
- 同一账号只能有一条排队记录，不可匹配自己；匹配池区分真人与机器人席位。
- 每次有效开始匹配时，服务器独立均匀随机取 3,000～8,000 毫秒的兜底时长，固定在该次 queue_ticket 上；客户端刷新、重连不重新取值，真正取消后重新排队才重新取值。
- 到截止前持续优先匹配真人；截止时原子检查有无可配真人，有则真人配对，无则创建 AI 对局。成功分配后立即移出队列，禁止迟到真人再加入或重复建局。
- 等待时展示“正在寻找对手”和取消按钮；不弹“人数不足”“转为人机”等提示，到点正常过渡到准备页。局内不显示“AI 陪练”角标，玩法说明中明确低峰时可能匹配自动对手；不使用“真人已加入”等误导文案。
- 3～8 秒是服务器决定兜底的时间，不保证客户端在网络异常时准点显示；分配失败明确显示重试，不能永久卡在匹配中。
- 匹配成功后直接进入准备页；对手基础资料由服务端返回。
- 取消与匹配成功冲突时，服务器原子决定：取消先完成则退出；配对先完成则返回房间信息，玩家可退出准备。不出现同时在大厅与对局的状态。
- 连续准备超时或主动离开准备累计达到 3 次/10 分钟，暂停在线匹配 60 秒并告知剩余时间；网络错误单独记录，初期避免扩大惩罚。

### 3.3.1 AI 对手规则

- AI 仅用于在线匹配兜底，好友房绝不自动加入 AI，真人退出后不由 AI 接管。
- AI 作为服务器控制的席位，遵守相同的四位谜底、命中反馈、先后手、补猜和局数上限。AI 在准备阶段独立随机生成并锁定谜底，不根据玩家谜底或猜测更改。
- 后端维护合成展示资料池：建议冷启动至少 300 个自然风格昵称及 50 个原创/授权插画头像，组合随机分配，避免同一玩家连续遇到完全相同的展示身份。不得冒用知名人物或营造现实好友身份。
- 资料池字段包含 display_profile_id、昵称、头像资源、来源、授权状态、启停状态；每局固定展示资料，不在对局中途换名，机器人账号与真人 user_id 严格隔离。
- 初版只用合成昵称与原创/授权头像，不批量提取注册用户资料。后续如支持用户贡献展示形象，需独立选择加入、明确用途、撤回后停止新局使用；只复制获准的展示字段，不复制真人账号身份、战绩或社交关系。
- 首版仅一个标准难度。策略输入仅包含 AI 自己的历史猜测及合法反馈、规则与随机种子，不可读取玩家谜底、玩家未提交输入或服务端判定函数的内部数据。
- 可实现方案：维护 0000～9999 的候选集合，每次依据自己收到的命中数量筛选一致候选；从候选中选取未猜过的组合。初次随机选择，后续在有限候选样本中比较信息收益，采用固定计算预算，避免穷举组合对造成卡顿。
- 思考展示时间建议随机 3～8 秒，运算与表现分离，按服务器截止时间调度；不刻意读取答案放水、不因玩家接近胜利而改变命中反馈。用内测数据调节策略强度。
- AI 准备延时建议 2～5 秒，真人未准备好时正常等待。AI 不伪造网络掉线；任务故障重试，无法继续按系统中止处理。
- 真人在 AI 局中断线/认输适用相同规则，AI 被视为有效在线席位。真人局与 AI 局战绩和指标分开统计，前台结算不附加 AI 角标，后台仍保留对手类型。
- AI 局可直接“再来一局”，新建 match_id、重设谜底、交换先手；无需模拟另一位用户点击同意。

### 3.4 密码匹配：好友口令房

为减少输入成本，“密码匹配”采用四位数字房间口令，不另加房间号和密码；输入四位后点击“加入房间”即加入，无房主审批。口令和谜底同为四位，通过页面和明确文案区分：大厅称“房间口令”，准备及局内称“我的底牌/对手密码”，不共用输入缓存。

- 创建后服务端分配随机四位口令，保留前导零；活动房间口令唯一。
- 可用口令为 0000～9999，共 10,000 个。按服务端原子分配，不使用碰撞后无限重试；房间存续期间保留口令，关闭后建议冷却 60 秒再复用。池满则提示“房间较多，请稍后创建”，不得分配重复口令。
- 口令本身是加入凭据，不是账号安全密码。输入正确且房间可加入时才允许进入。
- 房间仅两席，不进入公共匹配池。创建者展示口令、复制按钮、等待提示、关闭房间。
- 等待对手有效期 10 分钟，页面显示剩余时间；两人到齐即关闭口令加入能力并进入准备。对局期间即使知道口令也不能进入。
- 创建者在等待或准备时退出则关闭房间；加入者在准备时退出则房主回到等待，清除双方本局谜底并生成新口令和新的 10 分钟等待期。
- 准备超时按取消本局处理，双方返回大厅；不遗留半锁定房间。
- 输入错误、过期或关闭统一提示“口令无效或房间已关闭”；已满或对局中提示“房间暂不可加入”。
- 加入请求限速，默认同账号每分钟最多 10 次，另按 IP 及异常流量设服务端保护；合法用户不需要反复授权。
- 分享属于 P1；若增加房间卡片，必须由用户点击分享按钮触发，分享回调不作为好友已加入的证明。

## 4. 准备环节

界面包含双方头像昵称、对方状态（设置中/已准备）、四位输入格、自绘数字键盘、删除键、“随机生成”“锁定并准备”及 60 秒计时。

1. 每输入一位自动前进，可点格修改；不足四位时准备按钮禁用。
2. “随机生成”在本机生成合法四位数，仅用于便捷设置，仍需用户锁定。
3. 点击准备前展示“锁定后本局不可修改”的确认提示；提交中按钮禁用。
4. 服务端确认后锁定，显示“等待对手准备”；不能通过重连或重复请求更改谜底。
5. 双方准备完成，服务器创建本局、决定先手并发出开始事件；客户端显示 3 秒开场提示，首回合计时从服务器公布的开始时刻算起。

局内自己的四张底牌默认朝向自己，数字可见并标记“已锁定”；可一键盖牌保护屏幕隐私，盖牌后长按查看、松开遮挡。不能向对方下发谜底；双方准备事件只携带是否准备。

## 5. 猜测环节

### 5.1 第一视角牌桌布局

玩家像坐在桌子近端，对手位于桌子远端。对手头像/上半身剪影在上方，自己的手部或牌托在下方；第一视角不需要展示自己的完整人物。桌面采用近宽远窄的透视形状。

| 区域 | 内容与行为 |
| --- | --- |
| 上方远端约 20% | 对手头像、昵称、连接状态和四张背面朝我的底牌 |
| 中央桌面约 35% | 大轮数、当前行动方、最近三次猜测记录、独立猜测输入区；炸弹/密码装置缩为辅助装饰 |
| 下方近端约 15% | 自己的四张锁定底牌、自己的资料、盖牌/查看按钮 |
| 底部操作区约 30% | 自绘数字键盘、删除、提交按钮，保留安全区 |
| 记录区入口 | 常驻记录标题行提供“全部记录”；玩法和设置放左侧辅助菜单，认输在菜单内 |

比例为原型参考，适配时优先数字可读和键盘可点。对手回合可收起键盘，回到自己回合自动展开；不因收起改变数字牌的左右顺序。

- 手牌表示已经设置的谜底，每张固定对应一个位置，不能拖拽排序、交换或打出消耗。允许重复数字，牌没有花色点数限制。
- 准备时直接编辑自己的四张底牌并锁定；猜测时编辑桌面独立的四格“本次猜测”，不修改手牌。
- 下方手牌可轻微扇形排列，但不能遮挡数字。上方始终只显示牌背，结算前不逐位翻开，包括命中 1～3 位时。
- 桌中央使用“验证单”展示提交的数字，获得结果后盖上“命中 N/4”印章并收入历史；这是提交动作，不是把自己的底牌交给对手。
- “我的猜测”常驻在本次猜测输入区上方，按时间从旧到新显示最近 3 次；新记录加入后自然滚动，少于 3 次显示已有行，空状态提示“提交第一组数字，开始推理”。每行显示序号、四位数字及独立命中数，四列数字等宽对齐，不逐位染色。
- 点击“全部记录”后，在桌面中上区域展开可滚动的完整记录面板，提供“我的猜测/对手的猜测”页签，默认我的记录；收起对手人物装饰并缩小或暂时收起自己的手牌，保留查看底牌入口，为列表让位。
- 完整记录与底部本次猜测、数字键盘、倒计时同时可见可用，不使用遮住输入的全屏弹窗。返回常驻状态不清除草稿、不暂停计时、不修改底牌。
- 用户查看旧记录时不强制跳到列表底部；收到新记录显示“有新记录”提示，可点击回到最新。补猜阶段保持记录可用。记录只是权威历史，不自动推断正确位置或给出答案。
- 每条记录含行动序号、四位数字、命中 N/4；超时单独显示“本次超时”，不能当作 0/4。

双方可以查看双方已提交的猜测及各自对应反馈；两人谜底不同，历史按归属明确展示。首版不提供位置排除笔记或自动推理提示。

### 5.2 交互与状态

- 自己回合才能编辑并提交，等待时键盘禁用，显示“对手正在猜测”。
- 剩余 5 秒变色并可震动一次；静音/关闭振动后遵从设置。
- 提交进入等待确认状态；成功后新增一条历史、显示反馈并切换行动方。
- 仅历史数字整行呈中性色，命中数量作为独立徽标，不用四个位置逐个点亮制造额外提示。
- 非法输入、错误轮次和已结束提交均拒绝，不消耗额外机会，并同步最新状态。
- 没收到确认时查询状态或用同一请求 ID 重试；禁止自行推断结果后进入下一回合。
- 断线重连恢复已确认历史和剩余时间；未提交草稿可清空并提示“请重新输入”。

## 6. 结果与再来一局

结算展示：胜利/失败/平局/对局取消、明确原因、双方谜底、各自有效猜测次数、超时次数、总时长、完整记录。

正式对局结束后向这两位玩家揭晓双方谜底；准备取消及系统无效局不揭晓。展示谜底用于复盘，不在分析埋点中记录。

按钮规则：

| 来源 | 主按钮 | 次按钮 |
| --- | --- | --- |
| 在线匹配 | 再匹配一局 | 返回大厅 |
| 好友房 | 与好友再来一局 | 返回大厅 |

AI 对局的结果主按钮为“再来一局”，次按钮“返回大厅”，另提供“重新匹配”以重新寻找对手。

真人在线匹配结果可提供次级“与当前对手再战”，但不阻塞重新匹配。双方都请求再战才新建局；邀请有效期 30 秒，任一离开/超时则失效，不发送站外通知。下一局清空谜底、记录、超时次数，重新进入准备，并交换先后手。

若再战邀请与离开同时发生，以服务端状态为准。已经进入新的匹配或房间后，不接受旧局邀请。

首版后端保留胜/负/平和结束原因，系统中止与准备取消不计战绩；没有排行榜或竞技奖励。

## 7. 掉线、切后台与异常

原则：计时由服务器维护，切后台不暂停游戏，重连不能获得额外思考时间。

| 情况 | 产品行为 |
| --- | --- |
| 本机短时断线 | 展示恢复提示并自动重连；禁止新提交 |
| 对手断线 | 展示“对手连接中”，当前回合计时继续 |
| 连接失效 | 服务端心跳检测，默认每 5 秒心跳、连续 15 秒无心跳标记断线 |
| 重连宽限 | 从标记断线起 30 秒；恢复连接后取消该离线期限 |
| 单人离线到期 | 若对手在线，离线方判负 |
| 双方均离线 | 任一离线期限到期时若双方仍离线，中止对局，不计胜负 |
| 切后台但连接正常 | 计时照常，不因切后台立即判负 |
| 回合超时先发生 | 按回合规则空过；若达到连续两次超时则立即结束，无需等待重连期限 |
| 准备阶段掉线 | 保持共同 60 秒准备期限，不按正式局判负；超时取消 |
| 等待房掉线 | 房主离线宽限 30 秒，未恢复则关闭房间 |
| 服务端重启 | 能从权威快照恢复则恢复；不能恢复则系统中止，不将故障归因玩家 |
| 同账号另一设备登录 | 新会话接管，旧会话失效；同一玩家不能同时从两端行动 |
| 已结算后重连 | 返回原结算，不能重新开启或重复计分 |

所有终止事件按服务端顺序处理，第一条有效终止事件生效，后续事件不得覆盖结果。先手猜中仅进入补猜阶段，不能提前发送结算或揭晓谜底；已完成补猜条件的权威结算不会被后到的断线事件覆盖。补猜中系统故障仍按系统中止处理。

## 8. 技术实现要求与引擎选择

### 8.1 推荐 Cocos Creator 的原因

该项目主要是竖屏 UI、数字输入、牌桌分层动效以及联网状态同步，不需要复杂物理或 3D。Cocos Creator 官方提供微信小游戏构建入口、AppID 配置与资源发布流程，能够减少平台导出适配工作。[官方发布文档](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)

Godot 的官方 Web 导出面向浏览器；微信小游戏需额外适配。Godot 工具箱提供专用小游戏模板方案，可作为验证路线，但不应把普通 Web 导出当作微信包直接交付。[Godot Web 文档](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html)、[工具箱方案文档](https://get.godots.app/docs/app/minigame-engine)

因此推荐客户端 Cocos Creator + TypeScript；具体稳定版本在技术预研后锁定，不追求临时升级。若团队已有大量 Godot 资产或明显更熟悉 Godot，可保留 Godot，但必须先完成两端真机验证。当前仓库未见已有游戏源码，暂未发现迁移存量代码的成本。

### 8.2 系统边界

推荐首版采用客户端 + 单体权威游戏服务 + Redis 活跃状态/匹配队列 + 关系数据库用户和结算记录。服务端语言可选团队熟悉的 TypeScript 或 Go，不依赖客户端引擎，不为首版拆微服务。

- 客户端：输入、界面、动画、音效、平台登录桥接及网络状态展示。
- 服务端：身份校验、排队、口令分配、准备锁定、轮次推进、命中计算、超时、重连与结算。
- 通信：HTTPS 登录/配置，WSS 对局事件；使用微信支持的网络能力，真机验证域名、证书和连接行为。
- 结算记录持久化且幂等；客户端断线不影响服务端继续判定。

### 8.3 防泄漏与一致性

- 对手谜底只在服务端保存，正式结算前不放入客户端内存、快照、错误消息、埋点或日志。
- 客户端不得上传“命中数”“获胜标记”作为可信结果。
- 每条操作携带会话、match_id、turn_id、request_id；服务端检查身份、房间归属、阶段和截止时间。
- 同一房间事件串行化，并以递增 state_version 同步；客户端丢弃旧版本事件，缺口时取快照。
- 重复 request_id 返回同一处理结果，猜测最多消费一次机会；结果仅写入一次。
- 私房口令服务端限流、到期失效；日志屏蔽口令和谜底。无需为十进制四位谜底设计客户端“加密后公开”方案，短谜底容易被枚举。

### 8.4 最小数据与协议

| 对象 | 关键字段 |
| --- | --- |
| User | user_id、平台身份映射、昵称、头像资源、资料来源（微信/自定义/默认）、审核状态、资料版本、创建时间 |
| Room | room_id、模式、两位成员、房主、口令凭据、状态、过期时间、口令冷却时间 |
| Match | match_id、规则版本、双方锁定谜底（服务端私有）、先手、当前行动方、补猜状态、对手类型、AI 策略版本/私有随机种子、大轮/行动序号、deadline、state_version |
| Guess | match_id、player_id、turn_id、request_id、数字字符串、hit_count、处理时间、是否超时 |
| Result | match_id、胜者或空、结束原因、起止时间、双方统计 |

匹配票据额外记录 queue_ticket、入队时间、fallback_at、状态及分配结果；取消/真人配对/AI 分配竞争同一原子状态。

请求最少包括：登录、获取/保存资料、头像上传及审核查询、加入/取消匹配、创建/加入/离开房间、锁定谜底、提交猜测、认输、拉取状态、再战、心跳。

推送最少包括：匹配成功、成员变化、准备变化、开始、回合结果、连接变化、结算、房间关闭。快照只包含调用者可见信息；接口文档由研发在状态机确定后补充。

状态机：`等待成员 → 准备 → 开场 → 进行中 → [后手补猜] → 已结算`（后手正常猜中可从进行中直接结算）；等待和准备可进入`已取消`，系统故障可进入`已中止`。终态不可回退；再战生成新的 match_id。

活跃谜底仅用于对局和授权复盘；首版建议结算复盘保留 7 天，到期清除谜底与详细猜测，匿名聚合指标保留。具体保留时长和删除入口必须与最终隐私说明一致，不能无限期默认留存。

## 9. 视觉、音效与可用性

整体采用第一视角双人牌桌：暖色桌面、远端对手、近端手牌，中央放置数字炸弹/密码装置。用 2D 分层精灵、缩放、旋转和阴影表现空间感，首版无需真实 3D 房间、骨骼手指或自由镜头。对手形象使用通用角色剪影搭配个人头像，不承诺把用户头像生成真人模型。

### 9.1 交互动效规范

| 触发 | 表现 | 建议时长 |
| --- | --- | --- |
| 入座/开局 | 桌面轻推近，双方四张牌依次入位 | 600～900ms |
| 设置底牌 | 选中牌抬起，填数字轻弹，锁定后整体收拢 | 120～250ms |
| 切换行动方 | 桌灯/装置指示转向当前玩家，显示文字 | 200～350ms |
| 提交猜测 | 验证单滑向中央装置；等待服务器确认时保持提交中 | 250～400ms |
| 命中反馈 | 统一盖章“命中 N/4”，数字短暂放大 | 300～500ms |
| 后手补猜 | 装置亮起最后机会提示，底牌仍保持原可见性 | 300～500ms |
| 胜负/平局 | 最终结算后双方底牌翻开，胜方暖光、负方轻烟、平局双侧亮灯 | 800～1200ms |
| 查看记录 | 桌侧记事本抽屉展开 | 180～250ms |

[Cocos Tween 官方文档](https://docs.cocos.com/creator/3.8/manual/en/tween/index.html)支持位移、缩放、旋转等属性动画，可实现上述设计。以上时长为设计建议。

### 9.2 动效与状态边界

- 提交动作可以立即开始，但命中盖章、胜负和翻牌只由服务端确认触发；补猜阶段绝不提前翻对手底牌。
- 动效不改变回合计时。下一行动方获取状态后即可操作，上一条反馈可并行收尾，不锁住整个屏幕等待表演。
- 回合倒计时始终可见，盖章不遮挡输入、历史或提交按钮。不采用对应四个位置的命中灯，也不按正确位置播放特效。
- 重连直接渲染最新桌面，跳过旧动画；相同事件不重复盖章。切后台时停止视觉播放，回前台以快照恢复。
- 提供“简化动效”，去除镜头运动与震动，保留必要数字和状态反馈；低性能设备可自动降低粒子和阴影质量。
- 同一套卡牌按玩家视角映射到近端/远端，密码按所有者定义的左至右位置保存。对手结算翻牌时统一按 1～4 位阅读顺序呈现，不因透视或镜像反转为 4321。

### 9.3 美术交付清单

一张可适配桌面背景、远端通用人物/手部剪影、近端手部或牌托、牌背和牌面、动态数字字形、中央装置常态/警告/结算态、反馈印章、记录抽屉、头像框、按钮及少量粒子。先做灰盒验证手牌与猜测区是否易区分，再制作正式素材。

竖屏以 750×1334 为设计参考，顶部避让微信胶囊和刘海；所有页面右上角胶囊占位及外扩间距内不放自定义按钮、命中数或倒计时，背景可延伸。开发按实际平台菜单边界与屏幕安全区换算布局，不把概念稿固定百分比当作设备适配值，底部避让手势区；小屏优先保证输入与当前反馈可见，历史可滚动。按钮触控区以至少 44×44 逻辑像素为目标，并真机检查。

声音与振动独立开关，本地保存。音效只覆盖点击、提交、反馈、回合提醒、胜负；首次无声或播放失败不影响对局。颜色之外必须同时用文字区分当前回合、胜负与错误。

## 10. 性能与服务目标

以下是待验收目标，不代表平台硬性限制或已实现指标。

| 项目 | 首版目标与口径 |
| --- | --- |
| 启动 | 约定测试机与稳定网络下，冷启动至可操作大厅 P95 ≤ 5 秒，单独记录下载与登录耗时 |
| 交互 | 数字键点击本地反馈 ≤ 100ms；基础页面保持 30 FPS 以上 |
| 提交反馈 | 国内测试网络 RTT ≤ 100ms 时，从点击到权威反馈 P95 ≤ 500ms |
| 恢复 | 网络恢复后 5 秒内重建会话并拿到快照，仍以正式对局期限为准 |
| 对局一致性 | 不允许出现双赢家、重复计分、未轮到的猜测生效 |
| 容量 | 首轮压测目标 200 人同时在线、100 局同时进行，记录实际服务器规格与成本 |
| 包体 | 按当期微信平台限制验收；优先裁剪无关引擎模块、字体与音频，不在 PRD 固定可能过时的上限 |

最低设备/系统支持范围必须通过预研设备矩阵确定，再写入发布配置。至少覆盖 Android 中低端与主流机、iPhone 较旧支持机型与主流机型，以及不同长宽比。

## 11. 数据埋点与产品评估

事件：启动、资料授权结果、资料修改结果、登录成功/失败、查看规则、发起/取消/真人成功/AI兜底/失败匹配、创建/加入房间、准备开始/锁定/超时、对局开始、提交成功、行动超时、断线/重连、对局结束、点击再玩。

公共字段：匿名用户标识、会话、房间/对局标识、对手类型（真人/AI）、AI策略版本、规则版本、模式、客户端版本、平台、时间。事件按事件 ID 去重。分析平台不采集谜底、房间口令和原始猜测数字；猜测事件只记录次数、命中数和耗时。

| 指标 | 定义与用途 |
| --- | --- |
| 匹配成功率 | 真人配对率和 AI 兜底率分开统计，同时看等待分位数、取消率、分配失败率及实际兜底时长 |
| 准备转化率 | 正式开局数 / 双方到齐次数 |
| 自然结束率 | 猜中或同轮破解平局或上限平局局数 / 正式开局数，另列认输、超时、离线和系统中止 |
| 对局难度 | 有效猜测次数、时长 P50/P90、上限平局率 |
| 先手胜率 | 真人有效分胜负局中先手胜场 / 真人有效分胜负局数；另报同轮破解平局率和补猜成功率，按新手/熟练玩家分组 |
| 再玩率 | 结束后 60 秒内再次开始匹配或进入准备的用户数 / 到达结算的用户数 |
| 稳定性 | 重连成功率、系统中止率、崩溃率、提交延迟 |

上线前至少邀请 10～20 对真实玩家完成多局测试，重点检查是否误认为会提示正确位置、是否能够形成推理策略、是否感觉等待过长。小样本只用于发现体验问题，不直接宣称统计显著的平衡结论。

## 12. 验收清单

| 场景 | 必须满足的结果 |
| --- | --- |
| 0123 / 0453 | 返回 2/4；不暴露位置 |
| 0123 / 1230 | 返回 0/4 |
| 1122 / 1212 | 返回 2/4 |
| 0000 / 0000 | 返回 4/4；先手进入补猜，后手按是否为补猜判平局或胜利 |
| 少于/多于四位、非数字 | 客户端和服务端均拒绝 |
| 锁定后修改谜底 | 拒绝且原谜底不变 |
| 非行动方提交、伪造命中数 | 不生效，状态不前进 |
| 同一请求重发、双击提交 | 只产生一条有效记录 |
| 提交与截止同时发生 | 按服务器截止规则处理，双方看到一致结果 |
| 先手猜中、后手补猜也中 | 平局，补猜前不揭晓谜底 |
| 先手猜中、后手补猜未中/超时 | 先手胜；只给一次本轮机会 |
| 第 20 大轮后手猜中 | 先手未中则后手胜；先手已中则平局，不可提前按上限结算 |
| 第 20 大轮双方未中 | 平局；不比较最大命中数 |
| 连续两次自己行动超时 | 判负；中间有效提交能清零连续次数 |
| 取消匹配与配对竞争 | 最终仅处于一个状态 |
| 兜底阈值与真人匹配同时触发 | 只创建一局；分配前有真人优先真人 |
| 匹配重连、取消、再次匹配 | 重连复用截止时间；取消终止任务；新票据重新随机 |
| AI 决策输入审计 | 无玩家谜底；同规则补猜；后台对手类型准确，玩法说明披露自动匹配机制 |
| 微信资料拒绝/部分失败/不支持 | 缺失字段兜底，可继续；不覆盖用户自定义资料 |
| 编辑昵称/头像审核失败 | 旧资料仍生效，可重试；不阻塞对局 |
| 四位口令 0000、碰撞、池满 | 前导零保留；无重复分配；池满明确提示 |
| 两人同时加入最后一席 | 仅一人成功，房间最多两人 |
| 手动改猜测/拖拽手牌 | 猜测不改变底牌；手牌位置不可改 |
| 补猜、重连、简化动效 | 不提前翻牌、不重复播旧动画、不阻塞操作 |
| 口令失效或猜测限流 | 清晰提示，不创建错误房间 |
| 重连或换设备 | 恢复原局，不重复行动，不延长截止时间 |
| 客户端抓包与日志检查 | 结算前无法取得对手谜底 |
| 服务端故障 | 可恢复或明确中止，不错误计负 |
| 再战 | 新谜底、新记录、新 match_id，交换先手 |
| 最近三次记录与输入 | 记录正确、数字对齐、前导零保留；不暴露命中位置 |
| 全部记录与键盘同屏 | 滚动/切页/收起不丢草稿，倒计时不暂停，提交可用 |
| 微信胶囊安全区 | 所有页面自定义控件不与原生胶囊相交，横纵尺寸变化后仍可用 |
| 静音、无振动、小屏、刘海屏 | 不阻断玩法、不遮挡关键按钮 |

规则判定、状态迁移、幂等、并发加入、截止边界应有自动化测试；平台登录、切后台、真机输入和恢复应有真实设备验收记录。

## 13. 开发阶段与发布门槛

以下排期以 1 名客户端、1 名服务端并行开发，设计与测试提供支持为假设，工作量需要原型验证后重新估算，不含外部审核等待。

| 阶段 | 参考工期 | 可验收产物 |
| --- | --- | --- |
| M0 平台预研与规则原型 | 3～4 个工作日 | 确定引擎版本；资料能力验证；两台真机登录、WSS、后台恢复；灰盒牌桌及补猜试玩 |
| M1 核心对局 | 5～6 个工作日 | 固定房间双端准备、猜测、补猜、记录、结算；服务端权威判定 |
| M2 大厅及可靠性 | 5～7 个工作日 | 匹配、AI兜底、四位口令、资料编辑、重连、超时、再战、幂等及基础监控 |
| M3 内测与提审准备 | 5～7 个工作日 | 牌桌美术动效、AI及补猜体验测试、设备回归、压测、提审材料 |

新增个人资料、AI 和牌桌表现后，粗估 4～5 周完成可提审版本。若单人承担前后端，需重新排期；若保留 Godot，平台适配风险不能默认包含在上述估算中。

发布门槛：P0 全部通过；没有谜底泄漏或结算不一致；Android/iOS 真机闭环通过；能够监控错误并关闭新匹配；账号主体、类目、资质、隐私、必要的平台能力及审核项按小游戏后台当期清单逐项确认。无广告不等于自动豁免发布要求，本文不代替平台资质核验。

运营最小能力：维护开关、停止新匹配、兼容版本控制、规则配置、错误查询、按 match_id 排查状态与结束原因。维护默认不打断已有正常对局；紧急中止须显示系统原因且不计胜负。

## 14. 评审时优先确认的决策

1. 引擎：已确认 Cocos Creator + TypeScript，当前开发版本 3.8.8。
2. 数字：默认允许重复与前导零，降低输入解释成本。
3. 胜负：加入后手本轮补猜，双方同轮破解则平局；再战仍交换先手。
4. 节奏：建议准备 60 秒、行动 30 秒、20 大轮封顶平局，需试玩验证。
5. 口令：四位数字直接入房，最多两人，不额外增加房间号与密码双字段。
6. 资料：优先由用户触发微信资料获取，失败默认兜底；支持手动修改头像昵称，平台能力需预研验证。
7. 匹配：每次排队随机 3～8 秒无真人则 AI 兜底，不弹切换提示、不显示 AI 角标；规则说明披露自动对手机制。
8. 表现：第一视角双人牌桌，近端我的四张底牌、远端对手四张牌背，中央独立猜测区；2D 分层实现。

上述参数均由服务端规则版本控制；改动只影响新局，进行中的对局使用开局时锁定的规则。
